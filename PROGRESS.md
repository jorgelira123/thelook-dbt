## Decisions made and why
Full rationale in [docs/decisions.md](docs/decisions.md).
1. **dbt Core v1.12 locally + BigQuery** (not dbt platform/Cloud, not v2). Reason: the repo must show `profiles.yml`, targets and CI done by hand — Cloud hides exactly that. v1.12 is what most teams run and matches the bootcamp and the exam (1.11). The authoring layer (SQL/YAML/Jinja) is the same as v2. On Day 13 we run `--use-v2-parser` to prove v2 compatibility.
2. **Dataset:** `bigquery-public-data.thelook_ecommerce` (synthetic e-commerce: users, orders, order_items, products...). Clear grains, FKs to test `relationships`, timestamps for incremental.
3. **Billing enabled + cost guard:** low budget alert + `maximum_bytes_billed` in the profile.
4. **US location** for every dataset in the project (the public dataset is in US; BigQuery doesn't join across locations).
5. **SCD2 via our own copy of `products`** in `raw_thelook.products`: the public dataset doesn't change product prices, so we simulate a change with UPDATE on this copy between two snapshot runs. The copy stands for a Bronze table that, in a company, Airflow would load.
6. **Lean scope:** 4 staging, 2 intermediate, 4 marts, 1 snapshot.

## Planned models
- staging: `stg_thelook__users`, `stg_thelook__orders`, `stg_thelook__order_items`, `stg_thelook__products`
- intermediate: `int_order_items__enriched` (item + product → cost, margin), `int_customers__order_summary` (per-customer aggregates)
- snapshot: `snap_thelook__products` (SCD2 on `raw_thelook.products`)
- marts/core: `dim_customers`, `dim_products` (from the snapshot), `fct_orders` (table), `fct_order_items` (**incremental, merge, partitioned**)
- macros: `generate_schema_name` (dataset per layer/environment), `incremental_lookback` (incremental filter with a reprocessing window)
- tests: generic tests of all 4 types, 1 custom generic test, 2 singular (fct_orders × fct_order_items reconciliation; date ordering), 1 unit test

1. `git switch main && git pull` → `git switch -c day-NN-<topic>`
